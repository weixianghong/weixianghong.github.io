HNSW、NSG、Vamana、DiskANN 常被当成四个互不相干的算法名字背下来。但把它们摆在一起看，会发现是一条相当干净的演进线：

> **HNSW 和 NSG 解决「内存里的图怎么建最好」，Vamana 解决「怎么让图适配 SSD」，DiskANN 是围绕 Vamana 的整套磁盘系统。**

而且更进一步 —— 它们的邻居选择规则其实是**同一个判据的三个变体**。理解了这一点，这条线就通了。这篇文章就沿着这条线走一遍。

## 一、先把问题说清楚：为什么是图 {#why-graph}

高维近似最近邻（ANN）检索有四条经典路线：树（KD-tree、Annoy）、哈希（LSH）、量化与倒排（IVF、PQ）、图。在维度上百的稠密向量上，**图索引在「同等召回率下的 QPS」这个指标上大幅领先**，代价是内存占用大、构建慢、更新难。今天主流向量数据库（Milvus、Qdrant、Weaviate、pgvector、Lucene、Pinecone）的默认索引，几乎都是 HNSW 或 DiskANN 系。

> 顺带澄清一个容易混淆的分类问题：**ScaNN 是 Google 的库**，和 Meta 的 FAISS 是同一层级的东西，不是某个单点算法。只是它的招牌贡献恰好是一个量化算法 —— **各向异性向量量化**（ICML 2020）：在最大内积检索里，量化误差平行于数据点方向的分量会直接改变内积大小、直接影响排序，而正交分量影响小得多，所以损失函数应该给平行分量更大的权重，而不是一视同仁地最小化重构误差。同样的比特预算下召回明显更高。它走的是「分区 + 量化 + 精排」路线，不是图。

### 检索算法只有一个

图索引的检索永远是同一个算法：**贪心最好优先搜索**（greedy best-first search）。

```
GreedySearch(图 G, 起点 s, 查询 q, 候选池大小 L):
    候选集 C = {s};  已访问 V = {}
    while C 中存在未访问的点:
        p = C 中距 q 最近的未访问点
        V.add(p)
        C ∪= N(p)              # 展开 p 的邻居
        C 只保留距 q 最近的 L 个
    return C 的 top-k, 以及访问集合 V
```

![贪心最好优先搜索](/images/blog/ann-greedy-search.png)

HNSW、NSG、Vamana 在这一步上**没有任何区别**。区别全部发生在建图阶段。所以图索引的全部学问只剩一件事：

> **边，到底怎么连？**

要同时满足三个互相拉扯的目标：搜索要**走得到**（不陷在局部最优里）、要**走得快**（跳数少）、边还**不能太多**（内存和 IO 都有预算）。

## 二、理想答案和它的破产 {#delaunay}

理论上有一个完美答案：**Delaunay 图**。在 Delaunay 图上做贪心搜索，必然收敛到真正的最近邻，不会卡在局部最优。

问题是高维下 Delaunay 图几乎退化成完全图 —— 边数爆炸，完全不可用。

于是所有后续工作都在做同一件事：**用某种稀疏子图去近似 Delaunay 图**，在「精度」和「边数」之间找一个能落地的点。常用的近似是 **RNG**（相对邻域图）这类稀疏得多的邻近图。但 RNG 又带来了新问题，这就要先绕到小世界网络。

## 三、小世界：少量长边就能让直径塌缩 {#small-world}

### 名字从哪来

字面意思就是那句感叹 **"It's a small world!"** —— 你在异国他乡遇到一个陌生人，聊几句发现有共同的朋友，于是感叹「世界真小」。

学术源头是 1967 年 Stanley Milgram 的**小世界实验**：给美国中西部的一批人一封信，要求只能寄给自己认识的人、逐跳转交，最终送到波士顿一位指定的股票经纪人手里。成功送达的信平均只经过了 **6 跳** —— 这就是「六度分隔」。

### 严格定义

1998 年 Watts 和 Strogatz 给了形式化定义。一个图是「小世界」的，当它**同时**满足两个通常互相矛盾的性质：

![小世界图](/images/blog/ann-small-world.png)

构造方法很直观：从一个规则环形格出发，把每条边以概率 $$p$$ 随机重连到远处的节点。$$p=0$$ 是规则格（高聚类、长路径），$$p=1$$ 是随机图（低聚类、短路径），而**在中间一大段 $$p$$ 值上，只需要重连极少数边，平均路径长度就已经暴跌到接近随机图，而聚类系数几乎没掉**。

直觉上：社交网络里绝大多数朋友是「邻居的邻居」（高聚类），但只要有少数几个人搬去了外地，整个网络的直径就塌缩了。

### 关键的第二步：Kleinberg 的可导航性

这一步才是 HNSW 真正的理论根。2000 年 Kleinberg 指出了一个被忽略的问题：

> **短路径存在 ≠ 你能找到它。**

Milgram 实验真正惊人的地方不是「存在 6 跳的路径」（随机图里当然存在），而是**参与者仅凭本地信息 —— 只知道自己认识谁、目标住在哪 —— 就贪心地找到了它**。

Kleinberg 的模型是：在 $$d$$ 维格子上，每个节点除格子邻居外再加一条长边，长边连到距离 $$r$$ 处的概率正比于 $$r^{-\gamma}$$。他证明了：

- $$\gamma$$ 太小 → 长边太随机，跳出去以后不知道自己在哪，找不到方向；
- $$\gamma$$ 太大 → 长边太短，退化成规则格，跳数太多；
- **只有 $$\gamma = d$$ 时**，贪心路由的期望跳数是 $$O(\log^2 N)$$。

这个「能被贪心算法找到短路径」的性质就叫 **navigable（可导航）**，也就是 HNSW 里那个 **N**。

### 映射回 ANN

现在对照看向量检索：

- **kNN 图 / RNG** ≈ 规则格：聚类系数高（局部精度好），但直径大，从数据集一端走到另一端要 $$O(N^{1/d})$$ 跳；
- **缺的是**：少量长边，让搜索能一步跨越大半个数据集。

三个算法补长边的方式，正是它们的分野。但在讲分野之前，得先讲它们共用的那个东西。

## 四、同一个判据：遮挡剪枝 {#pruning}

插入一个点 $$p$$ 时，我们手里有一堆候选邻居，要从中挑出不超过 $$R$$ 个。**不能简单地取最近的 $$R$$ 个** —— 那样选出来的邻居会全部挤在同一个方向上，搜索一旦走错方向就再也回不来。正确的做法是保证邻居**在方向上是分散的**，这就是遮挡剪枝：

![遮挡剪枝](/images/blog/ann-occlusion-pruning.png)

$$
\alpha \cdot d(p^*, q) \leq d(p, q)
\quad\Longrightarrow\quad
\text{删除边} p \rightarrow q
$$

语义是：

> 如果我已经有一条通往 $$p^*$$ 的边，而 $$p^*$$ 到 $$q$$ 的距离比 $$p$$ 到 $$q$$ 的距离**小 $$\alpha$$ 倍以上**，那么「先走到 $$p^*$$，再从 $$p^*$$ 走向 $$q$$」是一次实质性的进展，我就不需要 $$p \rightarrow q$$ 这条直连边了。

$$\alpha = 1$$ 就是经典的 RNG 遮挡规则 —— HNSW 和 NSG 用的都是这个。

### 一维算例：α 到底改变了什么

设数轴上 $$p = 0$$，候选点在 $$1, 2, 4, 8$$ 处。

**$$\alpha = 1$$**：选中 $$a$$（距离 1）后，检查 $$d$$：$$1 \times 7 = 7 \leq 8$$，删掉。$$b$$、$$c$$ 同理被删。结果 $$N(p) = \{a\}$$ —— 出度只有 1，图退化成一条链，$$p$$ 走到 $$d$$ 要 4 跳。

**$$\alpha = 1.2$$**：检查 $$d$$ 时 $$1.2 \times 7 = 8.4 > 8$$，**保留**。结果 $$N(p) = \{a, d\}$$，$$p$$ 走到 $$d$$ 只要 1 跳。

为什么恰好是 $$d$$ 被保留？看比值 $$d(a,d)/d(p,d) = 7/8 = 0.875$$ —— 绕道 $$a$$ 只让剩余距离缩小了 12.5%，**收益不到门槛要求的 20%，不划算**，所以保留直连边。而绕道去 $$c$$ 能把剩余距离从 4 缩到 3（缩小 25% > 20%），划算，删掉直连边。

所以：

> **$$\alpha$$ 就是「绕路的最低收益门槛」。** 越靠外的点，绕道的相对收益越低（因为 $$d(p^*,q)/d(p,q) \rightarrow 1$$），越容易被保留成长边。

这意味着 α 剪枝是一个**自适应的长边生成器** —— 它不需要引入任何额外的数据结构，长边直接从判据里长出来。

真实高维数据上没有一维算例这么极端，但趋势完全一样：**纯 RNG 剪枝太贪心，把长边当成冗余删光了，导致图的直径偏大**。

### 三种长边来源

于是三个算法可以并排放在一起看了：

![三种制造长边的方式](/images/blog/ann-long-edge-strategies.png)

同一个剪枝判据，换个 $$\alpha$$、换个候选来源，就换了优化目标。下面逐个展开。

## 五、HNSW：用分层制造长边 {#hnsw}

Malkov 和 Yashunin 2016 年提出，前身是 NSW（可导航小世界图）。两个关键设计：

**(a) 分层结构。** 节点插入时随机抽一个层数

$$
l = \lfloor -\ln(\text{unif}(0,1)) \cdot m_L \rfloor,
\qquad m_L = 1/\ln M
$$

得到指数衰减的层数分布。第 0 层含全部点，越往上越稀疏。搜索时从顶层唯一入口开始，每层贪心走到局部最优，再下沉一层，最后在第 0 层用 $$ef_{search}$$ 大小的候选池做精细搜索。这模拟了跳表，把复杂度做到 $$O(\log N)$$。

**(b) 邻居选择启发式。** 就是上一节的遮挡剪枝（$$\alpha = 1$$）。这才是 HNSW 高召回的根本原因 —— 如果换成朴素的「取最近 M 个」，性能会断崖式下跌。

### 参数与工程特性

- **M**：每节点出度（第 0 层为 $$2M$$），典型 16~48。内存约 $$N \times 2M \times 4$$ 字节，再加原始向量。
- **efConstruction**：建图质量，128~500。
- **efSearch**：查询时的精度／速度旋钮，唯一的在线可调参数。

优点是**支持增量插入** —— 这是它统治工业界的最大原因 —— 实现简单、召回极高。缺点是内存占用大；删除只能打墓碑加定期重建；随机的层间跳转导致内存访问局部性差，**完全不适合放磁盘**。

### 一个值得知道的争议

2024 年有工作系统验证了：**在高维数据上，分层结构几乎没有贡献**。把 HNSW 拍平成单层图（只保留第 0 层加邻居启发式），性能基本不变；分层只在低维（小于 32 维）有明显收益。原因是高维图里天然存在「枢纽节点（hub）」，已经起到了长边的作用。

这个结论其实正是 NSG 和 Vamana 都采用**扁平单层图**的理论依据。

## 六、NSG：用搜索路径制造长边 {#nsg}

Navigating Spreading-out Graph（VLDB 2019）。明确提出四个优化目标：**保证连通性、降低平均出度、缩短搜索路径、减小索引体积**。

理论基础是作者提出的 **MSNET（单调搜索网络）**：如果图上任意两点间存在一条距离单调递减的路径，贪心搜索就不会回退。他们证明 **MRNG**（Monotonic RNG）是一种 MSNET，且期望出度是常数级。MRNG 的边选择规则形式上和 HNSW 的启发式几乎一样，区别在候选集的来源和整体框架。

### 构建流程

1. 用 NN-Descent / EFANNA 建一个近似 kNN 图作为基础；
2. 计算数据集的 **medoid（近似质心点）作为全局唯一导航点**；
3. 对每个点 $$p$$，**从导航点出发做一次贪心搜索**，把搜索路径上访问过的**所有点**（而不只是 kNN 邻居）作为候选池；
4. 对候选池施加 MRNG 剪枝；最后用一次 DFS 生成树补边，**强制保证全图连通**。

第 3 步是精髓：搜索路径上天然包含了「从入口到 $$p$$ 沿途的点」，其中有大量中远距离的点。这使得最终的图对「从导航点出发」这一固定搜索模式高度优化。**Vamana 后来直接继承了这个技巧。**

### 特点

扁平单层加固定入口，路径短、索引小（比 HNSW 小数倍），同召回下 QPS 通常优于 HNSW，是当年 ann-benchmarks 上的 SOTA。

致命短板是**纯静态索引**：要先建 kNN 图（本身就很贵），无法增量插入。这是它没能像 HNSW 那样普及的原因。后续的 **NSSG**（TPAMI 2021）改用角度剪枝，把建图开销降下来，且不再依赖高质量 kNN 图。

## 七、Vamana：用 α 制造长边 {#vamana}

### 先说名字

**Vamana（वामन）** 是印度神话中毗湿奴的第五个化身，梵语意为「侏儒」。故事是：阿修罗王 Bali 征服三界后举行献祭，侏儒 Vamana 前来只讨要「三步之地」，Bali 轻蔑地答应了；Vamana 随即化身巨人，**第一步跨过整个大地，第二步跨过整个天界**，第三步无处可放，Bali 献上自己的头。

DiskANN 出自 Microsoft Research India。论文本身没有解释命名，所以下面这层是社区的通行解读而非作者原话，但契合度高得不像巧合：**用极少的几步跨越整个空间** —— 这恰恰就是 Vamana 算法唯一的设计目标。

### 磁盘到底约束了什么

不理解这一节，后面所有设计选择都是天书。

**延迟账**：DRAM 随机访问约 100 ns，NVMe SSD 随机 4 KB 读约 100 μs（**慢 1000 倍**），目标端到端延迟 5 ms。

关键在于图搜索的读是**串行依赖**的 —— 必须读完当前节点、看到邻居列表，才知道下一个该读谁。所以能做的**串行往返次数只有 $$5\text{ms} / 100\mu\text{s} \approx 50$$ 次**。内存里的 HNSW 在 $$ef = 100$$ 时轻松访问上千个节点，照搬到磁盘上就是 100 ms 起步。

**还有一个更致命的问题**：图搜索每展开一个节点 $$p$$，需要计算查询到 $$p$$ 的**所有 $$R$$ 个邻居**的距离，才能决定下一步走谁。如果向量都在磁盘上，那么展开一个节点就等于 **$$R$$ 次磁盘读**（$$R=64$$ 就是 64 次）。这才是「图索引不能放磁盘」的真正原因，比跳数问题严重得多。

所以必须同时解决两件事：

1. **让跳数极少** → Vamana 的 α 剪枝负责；
2. **让「看邻居的距离」这一步不产生 IO** → 内存里的 PQ 码负责（下一节）。

### RobustPrune

```
RobustPrune(p, 候选集 V, α, 出度上限 R):
    V ← (V ∪ N_out(p)) \ {p}          # 现有邻居也扔回候选池重新竞争
    N_out(p) ← ∅

    while V 非空:
        p* ← argmin_{q ∈ V} d(p, q)     # 取候选中离 p 最近的
        N_out(p) ← N_out(p) ∪ {p*}      # 选它当邻居
        if |N_out(p)| = R: break

        for q in V:
            if α · d(p*, q) ≤ d(p, q):  # p* 遮挡了 q
                V ← V \ {q}
```

这个判据的漂亮之处在于它直接给出跳数上界。如果图满足「α-捷径可达」性质，那么从任意点贪心走向目标时，**每一跳都保证把剩余距离至少缩小 $$\alpha$$ 倍**（直到进入目标邻域），于是

$$
\text{跳数} \approx \log_{\alpha} \frac{\Delta}{\delta}
$$

$$\Delta$$ 是数据集直径，$$\delta$$ 是目标邻域半径。$$\alpha = 1.2$$ 时收缩很快；而 $$\alpha = 1$$ 时 $$\log_1 = \infty$$，**根本没有乘性收缩保证** —— 这就是 RNG 类图的跳数在理论上失控的原因。

代价是出度变大（长边占了名额），但**在磁盘场景这个交易极其划算**：出度从 32 涨到 64，邻居列表从 128 字节涨到 256 字节，反正一个 4 KB 扇区都装得下，读一次的成本完全一样；而跳数从 40 降到 15，直接省掉 25 次 100 μs 的往返。

> 这就是 Vamana 与 HNSW/NSG 的根本分歧：**内存图优化的是「访问了多少个点」，磁盘图优化的是「串行往返了多少次」。同一个剪枝规则，换个 α 就换了优化目标。**

### 完整建图流程

```
VamanaBuild(数据集 P, R, L, α):
    G ← 随机 R-正则有向图                     # ①
    s ← medoid(P)                             # 全局导航点

    for α' in [1.0, α]:                       # ②  两遍
        for p in random_permutation(P):
            _, V ← GreedySearch(G, s, p, L)   # ③  取"访问过的所有点"
            N_out(p) ← RobustPrune(p, V, α', R)
            for p' in N_out(p):               # ④  加反向边
                N_out(p') ← N_out(p') ∪ {p}
                if |N_out(p')| > R:
                    N_out(p') ← RobustPrune(p', N_out(p'), α', R)
```

**① 为什么用随机图初始化，而不是像 NSG 那样先建 kNN 图？**

两个原因。第一，**随机 $$R$$-正则图是扩展图，直径天然是 $$O(\log N)$$**，所以从第一次搜索开始就能到达全图任何地方；反观 kNN 图由紧密的局部团块组成，团块之间可能完全不连通，早期搜索会困在局部。第二，**省掉一整个昂贵的预处理阶段** —— NSG 必须先跑 NN-Descent 建近似 kNN 图，开销和建索引本身同一量级，Vamana 是自足的。

整个过程可以理解成**从随机退火到有序**：初始全是随机长边，每一轮把无用的随机边替换成有用的边，而 α 判据保证真正有价值的长边被保留下来。

**② 为什么要两遍，第一遍还偏偏用 α = 1？**

第一遍用最严格的 RNG 规则，快速建立**高质量的局部结构**。这一步做完后，第二遍的贪心搜索才能返回**有意义的访问集合**（在纯随机图上搜索，访问集合基本是垃圾，拿垃圾去做 α 剪枝毫无意义）。第二遍再在好材料上做放松剪枝，精准注入长边、压缩直径。论文的消融实验显示：单跑一遍 $$\alpha = 1.2$$ 明显差于两遍。

**③ 为什么候选集用「访问集合」而不是「搜到的 top-L 近邻」？**

这是从 NSG 继承的技巧，理由同上一节：只喂 top-L 近邻，候选里根本没有远点，长边无从谈起。

**④ 反向边为什么必须加？**

RobustPrune 只决定了 $$p$$ 的**出边**。如果只有出边，会出现这样的灾难：某个点可能没有任何入边，那它就**永远不可能被搜索到**，即使它是某个查询的真正最近邻。加反向边保证「我连你，你也连我」（在出度允许范围内），图近似双向，连通性得到保障。反向边可能把邻居的出度撑爆，所以要对它再剪一次枝 —— 这是构建期的主要开销来源之一。

## 八、DiskANN：把图搬上 SSD {#diskann}

Vamana 只是一张图。DiskANN = Vamana + 存储布局 + beam search + PQ，目标是**单台 64 GB 内存的机器加一块普通 SSD，索引十亿级向量，recall@1 超过 95%，延迟低于 5 ms**。

### 数据放在哪

![DiskANN 的内存 / 磁盘分工](/images/blog/ann-diskann-layout.png)

内存里只有近似信息，磁盘上是全部精确信息。

节点 $$i$$ 在 SSD 上存成一条**定长记录**，起始偏移 $$= i \times \text{node\_size}$$，直接算出来，不需要任何额外索引结构。这个布局是点睛之笔：一次 4 KB 读同时拿到「**我在哪**」（原始向量，用于精确重排）和「**往哪走**」（邻居列表，用于继续搜索）。精确向量是**免费搭车**来的 —— 反正为了拿邻居列表这个扇区本来就必须读。

### BeamSearch

```
BeamSearch(查询 q, 候选池大小 L, beam 宽度 W):
    C ← 优先队列 {medoid}, 按 PQ 近似距离排序, 容量 L
    V ← ∅                      # 已展开（已读盘）的节点
    Exact ← ∅                  # (id, 精确距离)

    while C 中存在未展开的节点:
        B ← C 中距离最近的 W 个未展开节点       # 组一个 beam
        并发发起 W 次 4KB 异步读, 等待全部返回   # 一次 IO 往返

        for each 读回的节点 b:
            Exact.add(b.id, d(q, b.raw_vector))     # ★  精确距离
            for n in b.neighbors:
                if n ∉ V and n ∉ C:
                    C.insert(n, PQ_dist(q, n))      # ★★ 纯内存计算, 零 IO
            V.add(b.id)
        C 截断到 L

    return  Exact 中精确距离最小的 top-k
```

![一轮 beam search](/images/blog/ann-diskann-beam-search.png)

两个星号就是全部的魔法：

**★★ 展开邻居时用内存 PQ 距离。** 一个节点有 64 个邻居，如果要读它们的真实向量就是 64 次磁盘读；改成查内存里的 PQ 码，是 64 次约 100 ns 的访问（还能 SIMD 查表加速），相比一次 100 μs 的磁盘读可以忽略。**总磁盘读次数 = 展开的节点数，而不是节点数 × 64。**

**★ 精度靠精确距离兜底。** PQ 有量化误差，会把候选顺序排错。但 PQ 距离**只用来决定「下一步走谁」和「候选池留谁」**，最终返回的 top-k 是从 `Exact` 集合里按**精确距离**选的，而 $$|\text{Exact}| \approx$$ 几百，远大于 $$k = 10$$。所以 PQ 误差只会导致「路走得不够优」，不会导致「排序错误」。

> **近似距离负责导航，精确距离负责定序。** 这个解耦是 DiskANN 能用 32 字节压缩码达到 95%+ 召回的根本原因。对比之下，HNSW + PQ 方案里 PQ 误差会直接进入最终排序，精度损失大得多。

### 延迟账，对上了

$$
\underbrace{200}_{\text{展开节点数}} \div \underbrace{4}_{W}
= 50 \text{ 轮 IO 往返}
\times 100\,\mu s
\approx 5\text{ ms}
$$

正好卡在预算上。如果用 $$\alpha = 1$$ 的图，跳数翻两三倍就是 15 ms，方案不成立 —— **α 剪枝不是锦上添花的优化，是这个系统能否成立的前提。**

**beam 宽度 $$W$$ 是最重要的在线旋钮**：$$W$$ 大则往返轮数少、**单查询延迟低**，但每轮会读一些本来不会访问的节点，总读量上升、**吞吐下降**。所以低延迟场景调大（4~8），高吞吐批量场景调小（1~2）。

### 十亿级怎么建：分片合并

建图本身要把数据放内存（贪心搜索要算精确距离），十亿点显然放不下。做法是：

1. 在采样集上跑 k-means 得到 $$k$$ 个中心（SIFT1B 上论文用了约 40 个）；
2. 每个点分配给**最近的 2 个中心**（重叠因子 $$\ell = 2$$），每个分片约 $$2N/k$$ 个点，能塞进内存；
3. 每个分片**独立建 Vamana 图**；
4. **合并**：对同时出现在分片 A、B 中的点 $$v$$，令 $$N_{out}(v) = \text{RobustPrune}(v,\ N_A(v) \cup N_B(v),\ \alpha,\ R)$$。

**重叠是关键**。如果每点只属于一个分片，分片之间就完全不连通，搜索无法跨越簇边界；有了重叠，边界点同时携带两边的边，成为天然的桥。论文报告这种合并式构建能达到单体构建约 95% 的质量。

### 家族演进

| 工作 | 解决的问题 |
|---|---|
| **FreshDiskANN**（2021） | 增量更新。内存中的可读写临时索引 + SSD 长期索引，后台 StreamingMerge 周期性合并 |
| **Filtered-DiskANN**（WWW 2023） | 带属性过滤的检索。建图时就让边覆盖各标签子集，避免「先搜后过滤」召回崩塌 |
| **OOD-DiskANN** | 查询分布与底库分布不一致（如跨模态检索） |
| **SPANN / SPFresh** | 同一团队的另一条路线：倒排 posting list 放 SSD，不是图，适合更新频繁的场景 |

顺带说一个巧妙的细节。图索引删点的难处在于：删掉 $$p$$ 后所有指向它的边都断了，图会出现空洞甚至断连。FreshDiskANN 的 **consolidate** 做法是**让邻居继承被删点的邻居** —— 对每个有边 $$u \rightarrow p$$ 的节点 $$u$$：

$$
N_{out}(u) \leftarrow \text{RobustPrune}\big(u,\ (N_{out}(u) \cup N_{out}(p)) \setminus \text{已删除集合},\ \alpha,\ R\big)
$$

原本经过 $$p$$ 的路径被局部修补成绕过 $$p$$ 的路径，连通性和可导航性都得以保持。这个操作在后台批量做，不阻塞查询。

落地场景包括 Azure AI Search、Cosmos DB、Bing、Milvus 的 DISKANN 索引、pgvectorscale 的 StreamingDiskANN 等。

## 九、对比与选型 {#choose}

| | HNSW | NSG | Vamana / DiskANN |
|---|---|---|---|
| 图结构 | 多层 | 单层扁平 | 单层扁平 |
| 入口点 | 顶层随机节点 | medoid（固定） | medoid（固定） |
| 剪枝规则 | RNG 遮挡（α=1） | MRNG（α=1） | **α 放松遮挡（α≈1.2）** |
| 初始图 | 边插边建 | 需先建 kNN 图 | **随机正则图** |
| 长边来源 | 分层 | 搜索路径候选 | α 判据 |
| 出度 | M / 2M | 较小、可变 | 固定上界 R（较大） |
| 增量插入 | 原生支持 | 不支持 | 需 FreshDiskANN |
| 目标介质 | 内存 | 内存 | **SSD** |
| 主要优势 | 通用、易用、生态最好 | 内存态 QPS / 索引体积最优 | 单机十亿级，成本低 1~2 个数量级 |
| 主要劣势 | 内存贵、删除难 | 建图慢、不可更新 | 建图更慢、延迟受 IO 下限约束 |

### 选型

- **数据量小于一千万、内存放得下、需要频繁增删** → **HNSW**。没有悬念，生态和运维成熟度碾压。`M=16~32, efConstruction=200`，线上调 `efSearch`。
- **数据量一亿以上，或内存成本是瓶颈，且更新不频繁** → **DiskANN**。典型配置 `R=64~96, L=100, α=1.2`，PQ 码长按内存预算定（内存里的 PQ 码总量最好不超过可用内存的一半）。需要更新就上 FreshDiskANN / StreamingDiskANN。
- **纯静态底库、极致追求内存态 QPS**（离线批量检索、固定物料库的召回）→ **NSG / NSSG** 值得一试，但要接受生态较弱、需要自己维护。
- **有 GPU 且要极高吞吐** → 看 NVIDIA 的 **CAGRA**（RAFT / cuVS），为 GPU 并行访存重新设计的图索引，可导出成 HNSW 格式在 CPU 上检索。

### 一个常见误区

给 HNSW 挂上 PQ 压缩来省内存（HNSW + PQ）。这条路的精度损失通常比 DiskANN 大得多，因为 HNSW 缺少 DiskANN 那种「用原始向量重排」的兜底步骤 —— 量化误差会直接进入最终排序。如果内存真的紧张，优先考虑 DiskANN，而不是压缩 HNSW。

## 收束

回头看，这四个名字其实只讲了一件事：**在一张必须稀疏的图上，如何保住可导航性。**

- Delaunay 图能保证贪心收敛，但高维下太稠密 → 必须稀疏化；
- RNG 式的遮挡剪枝能稀疏化，但把长边删光了 → 直径失控；
- 补长边有三种办法：**加一层结构**（HNSW）、**换候选来源**（NSG）、**改判据本身**（Vamana）；
- 而当介质从 DRAM 换成 SSD，优化目标从「访问点数」变成「串行往返次数」，第三种办法就成了唯一解 —— 再配上「内存近似导航 + 磁盘精确定序」的解耦，就是 DiskANN。

判据始终是同一个。变的只是 α，和你在为哪一种介质做优化。
